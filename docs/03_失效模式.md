# 03 · 失效模式与防复发

> 本方案是**从一次真实故障里长出来的**。本文记录：故障链、根因、修法、以及防复发清单。
>
> **为什么单列一篇**：这个失效模式**不出声**（不报错、不崩溃），
> 只是让正文里的代号**悄悄变成天书** —— 属"静默失效"类，最贵的那种病。

---

## 一、故障链（真实发生 · 可复现）

### 1.1 场景

Agent 的常驻记忆文件（每轮注入 system prompt）里，用**缩写代号 + 内嵌字典**做压缩：

```
┌─ 正文 ────────────────────────────┐
│ …用 RL-3 / GUARD-2 / BREAKER 等… │
│                                   │
│ ## 概括词字典                     │  ← 字典内嵌在【文末】
│ RL-3    ｜ 三条红线…              │
│ GUARD-2 ｜ 两层防护…              │
└───────────────────────────────────┘
```

### 1.2 故障步骤

| 步 | 发生什么 |
|:--|:---|
| 1 | 记忆持续增长，正文 + 内嵌字典**合计超过注入上限**（本仓：单文件 20,000 字符） |
| 2 | 系统**静默截断** —— ⚠️ **从尾部切**，不报错、不警告 |
| 3 | 字典排在**文末** → **字典最先被切掉** |
| 4 | 正文里的代号**全部失去定义** → 对模型而言是**一串无意义符号** |
| 5 | 模型仍会"自信地用"这些代号 —— **不知道自己读的是天书** |

### 1.3 为什么这个故障特别贵

| 特性 | 后果 |
|:---|:---|
| **不出声** | 没有任何报错，看起来"文件正常" |
| **不崩溃** | 模型照常输出，只是**依据被掏空** |
| **方向误导** | 排查时会怀疑"模型能力"，而非"注入被截" |
| **概率性** | 只在超限时发生 → **平时一切正常**，难以复现定位 |
| **破坏面大** | 一次性作废**全文所有**代号（不是局部） |

### 1.4 修复前的"缓解"（不彻底）

**曾用对策**：把字典**从文末上移到靠前位置**。

```
修法：字典从 L1625+ 移到 L1625 之前（身份信息后、正文内容前）
```

**为什么只是缓解**：
- ✅ 字典**不再最先被切**
- ❌ 但字典**仍占 16.1% 的注入额度** → **挤压正文**
- ❌ 只要总量还在涨，**正文迟早还是会被切**（只是换个东西被切）

> **本质问题没解决**：**"字典和被压缩内容共用同一份预算"** → 零和。

---

## 二、根因分析

### 2.1 直接根因

```
字典放置位置与"截断方向"冲突：

    截断方向：尾部 → 头部（先切尾）
    字典位置：文末              ← 💥 正好在最危险的位置
```

### 2.2 深层根因（两句话）

| # | 根因 | 说明 |
|:--|:---|:---|
| 1 | **零和假设** | 默认"字典和被压缩内容必须共处一个文件" → 二者必然互相挤压 |
| 2 | **未把"截断"当失效模式** | 只考虑了"总窗口够不够"，**没考虑"不够时会怎么坏"** |

### 2.3 一句话

> **把解释性内容（字典）和被解释内容（正文）放进同一个有限预算里，
> 就必然制造出"谁把谁挤掉、以及谁先被切掉"的问题。**

---

## 三、修法（根治）

### 3.1 核心动作：**字典外置**

```
修复前                              修复后
┌────────────────────────┐         ┌────────────────────────┐
│ 正文（含代号）          │         │ 正文（含代号）          │
│ …                      │         │ …                      │
│ ## 概括词字典（3,196 字符）│      │ **词表（29）**：RL-3、  │ ← 只留词名
│ RL-3   ｜ 三条红线…     │         │ GUARD-2、…（262 字符）  │
│ GUARD-2 ｜ 两层防护…    │         │ → 详见 字典文件（指针） │
└────────────────────────┘         └────────────────────────┘
                                              │ 按需读取
                                              ▼
                                   ┌────────────────────────┐
                                   │ 外部字典文件（3,599 字符）│
                                   │ 词 ｜ 含义 ｜ 详情路径   │
                                   └────────────────────────┘
```

### 3.2 为什么这样能根治

| 原问题 | 外置后 |
|:---|:---|
| 字典占 16.1% 额度 | **占 0**（不常驻）→ 正文腾出 ~2.9K 字符 |
| 字典可能被截断 | **字典独立成文件 → 不受正文截断影响** |
| 字典增大 → 正文减少（零和） | **字典增长不再挤压正文** |
| 代号被切 → 全变天书 | **索引极短（262 字符），截断风险大幅降低**；且**字典文件永远完整** |

### 3.3 实测结果（本仓 2026-09-24）

| 指标 | 修复前 | 修复后 |
|:---|:---|:---|
| 正文内字典占用 | **3,196 字符**（16.1%） | **262 字符**（索引行） |
| 净腾出额度 | — | **约 2.7~2.9K 字符** |
| 字典完整定义 | 在正文里（有被切风险） | **独立文件 3,599 字符**（不被切） |
| 词数 | 27 | **29**（可持续增长，不挤压正文） |
| 截断后果 | 🔴 代号变天书 | 🟢 索引在、字典完整 |

### 3.4 附带收益：**同时根治了"文档自相矛盾"**

⚠️ 外置不只是"搬个文件" —— **必须同步所有提到该机制的规则**，否则文档互相打架。

**本次同步的 4 处**（真实清单，可照抄）：

| # | 位置 | 原内容 | 改为 |
|:--|:---|:---|:---|
| 1 | 记忆文件头部 | （无指引） | 指向外置字典 + 用法三步 |
| 2 | 工作流 §三 | "字典与被压缩内容**放同一文件**" | "**索引在内 / 字典在外**" |
| 3 | 工作流 §七 | "字典**必须靠前放**" | 改为外置说明 |
| 4 | 工作流 §九 | 风险 V1 "字典会被截断" | 标为 **✅ 已根治** |

> **教训**：**机制变了，引用该机制的文档必须同步改** ——
> 否则规则之间自相矛盾，后来者不知道该听哪个。

## 四、防复发清单

### 4.1 设计期（建这套机制时）

```
□ 字典是否【不在】被压缩文件内？        ← 首要
□ 正文里的索引是否 ≤ 300 字符？
□ 代号是否【只增不改】（历史正文可读性）？
□ 每条字典项是否都给了【可解析的真实路径】？
□ 是否有【加词查重】机制（严禁一概念两代号）？
□ 是否控制了总注入（留出安全余量）？
```

### 4.2 运行期（每次压缩后）

```
□ 跑可达性校验：字典每条路径必须真实存在
□ 核对正文内索引词名 与 字典词条 是否一致（无孤儿、无缺失）
□ 确认正文总量距上限仍有【安全余量】
```

### 4.3 变更期（搬迁 / 改名 / 拆分）

```
□ 旧路径已不存在（断言）
□ 新路径已生效（断言）
□ 所有【引用点】已更新（脚本 / 文档 / 配置 / 计划任务）
□ 字典文件已随之迁移，且路径仍可解析
```

> 这几条属通用"静默失效防治"（可参见 M-05 类规范）。

## 五、其他已知失效模式

| # | 失效 | 症状 | 防法 |
|:--|:---|:---|:---|
| 1 | **索引膨胀** | 词太多 → 索引行变长，重蹈"占额度"覆辙 | 索引设上限（如 ≤300 字符）；超了并入字典文件 |
| 2 | **路径悬空** | 字典指向的文件被改名/搬迁 → 代号查不到详情 | **强制可达性校验**（可机器化） |
| 3 | **一词两表 / 一概念两代号** | 同一概念存在两个代号 → 语义分裂 | **加词先查重**；定期去重 |
| 4 | **代号污染** | 代号与正文里的普通词冲突被误替换 | 代号用**不易撞车**的形式（大写+连字符） |
| 5 | **字典被误删/漏迁** | 字典文件丢失 → 全部代号失效 | 字典与正文**同库同版本管理**（如一并纳入 git） |
| 6 | **无人维护** | 词只加不清理 → 死词堆积 | 定期审：**有路径失效 / 长期未引用**的词可退役 |
| 7 | **过度压缩** | 为省 token 把不该压的也压了 → 可读性崩 | **只压高频长概念**；低频不编 |

## 六、可复现性（怎么自己验一遍）

### 6.1 故障模拟（验证"字典内嵌会死"）

```
1. 建一个接近上限的正文文件（如 19,500 字符）
2. 在【文末】放一段"代号 → 定义"的字典（如 1,500 字符）
3. 让总量超上限（20,000）→ 触发截断
4. 观察：字典被切 → 正文里的代号无定义
   ✅ 若观察到此现象，说明故障链复现成功
```

### 6.2 修法验证（验证"外置能活"）

```
1. 把字典移出正文 → 独立文件
2. 正文只留"词名索引"（几十~几百字符）
3. 再次触发超限 → 截断
4. 观察：
   ✅ 索引在（或至少字典文件完整可读）
   ✅ 代号仍可展开
```

### 6.3 校验脚本（可达性）

```python
# 伪代码：字典里每条路径必须真实存在
for word, meaning, path in dictionary:
    assert os.path.exists(path), f"[{word}] 路径悬空: {path}"
```

**本仓实测结论**：修复后跑该检查，**29 条词典路径全部可达**（外部路径已在白名单内豁免）。

## 七、教训（写给未来的自己）

1. **"不出声的失效"最贵** —— 它不崩溃，只是让依据悄悄消失
2. **"缓解"不等于"根治"** —— 把字典靠前放，只是把问题推迟
3. **零和结构必须打破** —— 两个东西抢一份预算，迟早出事；**把它们分到不同预算里**
4. **机制改动必须同步所有引用点** —— 否则文档自相矛盾，后来者无所适从
5. **校验要能机器化** —— "路径是否可达"这种判据，**不能靠人记**
6. **诚实记录故障** —— 这个方案的价值，一半来自"我们真的踩过这个坑"

**口径说明**：「代号替换」本身的收益**取决于概念重复频次** —— 重复越多、代号越短，收益越大；
本方案的**确定性收益来自「外置」**（省下字典本身的常驻成本），**增量收益来自「替换」**。
