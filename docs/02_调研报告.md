# 02 · 调研报告

> 三个问题：**这想法有没有应用场景？谁在做相近的事？我们的位置在哪？**
>
> ⚠️ 本文引用均为**外部资料**（检索所得），仅作定位与对比；
> 本方案的具体做法与实测数据来自本项目自身实践。

## 一、结论先说

| 问题 | 结论 |
|:---|:---|
| **有应用场景吗？** | ✅ **有，而且是被行业硬约束逼出来的刚需** —— 主流 agent 框架**全都**给常驻记忆设了硬上限，且**超限静默截断** |
| **有人做过吗？** | ✅ **核心思想有高度同源工作**（缩写字典 + 无损可逆） |
| **我们是原创吗？** | ⚠️ **不是全新概念，但有一个明确空白是我们的**：**"字典外置 + 惰性加载 + 以截断安全为设计目标"** —— 现有工作**无一例外把字典放在 prompt 内部** |

## 二、应用场景（有真实需求证据）

### 2.1 场景 A · Agent 启动记忆的硬上限 ← **最强适用**

**这是被行业实践验证的刚需** —— 主流实现**都**给常驻注入设了上限：

| 实现 | 上限 | 超限行为 |
|:---|:---|:---|
| **本仓宿主** | 单文件 **20,000 字符** / 合计 **60,000** | **静默从尾部截断** |
| **Claude Code** | `MEMORY.md` 索引**前 200 行或 25 KB** 载入 | 超出部分不载入 |
| **Hermes Agent** | `MEMORY.md` **2,200 字符**（~800 token）/ `USER.md` **1,375 字符** | **写入即报错**（不静默丢），由 agent 自己腾空间 |

**关键观察**：
- 三家**都设了硬上限** → 说明"常驻注入额度稀缺"是**普遍约束**，不是本仓特例
- **Hermes 用"报错"而非"静默截断"** → 更友好，但**没解决"额度不够用"**（只是不偷偷丢）
- **Claude Code 与 Hermes 都是"agent 自维护的记忆文件"** → 与我们的场景**同构**

> **推论**：只要 agent 长期运行、记忆持续增长，就**必然会撞上限**。
> 本方案针对的正是这个**已被三方独立确认的约束**。

### 2.2 场景 B · 长文档 / RAG 上下文

**文献密集覆盖**（也是竞争最激烈的战场）：
- LLMLingua 系列、LongLLMLingua、CPC、ProCut、CodePromptZip…
- 实测收益：输入 token 降 30~80%

⚠️ **但这里有个重要警告（文献实测）**：

> **「压缩悖论」** —— arXiv:2603.23525（预注册随机对照试验，358 次生产运行）：
> - **温和压缩**（保留率 0.5）→ 总成本 **降 27.9%** ✅
> - **激进压缩**（保留率 0.2）→ 总成本 **反升 1.8%** ❌（因**输出 token 膨胀**）
>
> **结论：`"压得更狠" 不是可靠的生产启发式`** —— 必须把**输出 token** 当一等公民来看。

**对我们的意义**：本方案属**温和无损**路线，天然避开该陷阱（不制造语义模糊 → 不诱发输出膨胀）。

### 2.3 场景 C · 重复性数据 / 日志分析

**Dict-Encoding 论文**（arXiv:2604.13066）实测：
- 压缩率 **60~80%**，LogHub 2.0 基准上精确匹配率 **> 0.99**
- **关键**：压缩率只解释 <2% 的相似度方差 → **质量取决于数据特性，不取决于压缩强度**

**意义**：重复模式越多，收益越大 —— 与我们的判断一致（**只对高频概念编码**）。

### 2.4 场景 D · Agent 指令文件封装（工程化）

- **`context-compress`**（GitHub）：专压 **agent 指令文件**（CLAUDE.md、steering files）
  - 实测：prose-heavy 降 **40~70%** ｜ already-lean 只降 **2~7%**
  - 组合收益（压缩 + 去重）：61KB 栈省 **~37%**（~6,000 token/会话）
  - **重要观察**：**"已经很精简的文件"几乎压不动**（2-7%）→ 说明**朴素压缩有天花板**

**意义**：该工具用 **LLM 改写 + 去重**（**有损**）；我们是**无损映射**，可与之**互补**而非竞争。

---

### 2.5 场景判别表（什么时候该用）

| 条件 | 适用度 |
|:---|:---|
| **每轮都要注入** + **概念反复出现** | ✅✅ **强适用**（本方案主战场） |
| 有**硬上限**且**静默截断** | ✅✅ 强适用（截断安全是我们的独有收益） |
| 按需检索的内容（RAG） | ✅ 适用（但竞争激烈，且有压缩悖论风险） |
| 一次性内容 | ❌ 不适用（无重复 → 无收益） |
| 纯散文，面向人类阅读 | ❌ 不适用（代号破坏可读性） |
| 已极精简（无冗余） | ⚠️ 收益接近 0（工具有实测：2~7%） |

## 三、相关工作（分层对照）

### 3.1 最同源：**字典 / 缩写编码**路线

| 工作 | 出处 | 做法 | 字典位置 | 需微调 |
|:---|:---|:---|:---|:---|
| **Lossless Prompt Compression via Dictionary-Encoding & ICL** | arXiv:2604.13066（2026-03） | 高频子序列 → meta-token `⟨M#⟩`；**system prompt 给字典**，LLM 上下文内学会解读 | **system prompt 内** | ❌ 免微调 |
| **CompactPrompt** | arXiv:2510.18043（ACM ICAIF'25） | LZW 式 n-gram 缩写；可逆字典；**支持原位还原** | **文档内**（metadata table） | ❌ |
| **Harvill et al. 2025**（据 2604.13066 引述） | — | 首个**无损**输入压缩；重复子序列→meta-token，18~27% token 降 | — | ⚠️ **需微调** |
| **IBM Prompt Compression 教程** | IBM Think（2026-05） | 实务建议含 **"用缩写（如 days→d）"** | 隐含 | ❌ |

> **⭐ 最重要的观察**：
> **2604.13066 明确点出了自身局限** —— 引用 Harvill et al. 时写道：
> *"their approach requires fine-tuning the LLM to understand placeholder token meanings,
> creating a fundamental scalability limitation."*（需微调才能理解占位符 = 根本性扩展瓶颈）
>
> **它的解法正是**：把字典放进 system prompt，让 LLM **上下文内学**（免微调）。
> **但这仍把字典塞进了 prompt 内部** —— 字典本身**照旧占用上下文额度**。

**→ 这就是我们的空白位置。**（见 §四）

### 3.2 token 剪枝路线（有损）

| 工作 | 出处 | 压缩率 | 代价 |
|:---|:---|:---|:---|
| **LLMLingua** | EMNLP'23（Microsoft，GitHub 6.6k⭐） | 最高 **20×** | **有损**；需小模型；需按 prompt 结构调参 |
| **LongLLMLingua** | ACL'24 | 1/4 token 下 RAG **+21.4%** | 有损 |
| **LLMLingua-2** | ACL'24 | 3~6× 更快、任务无关 | 有损；蒸馏自 GPT-4 |
| **CPC**（上下文感知句编码） | AAAI-25 | 比 token 级**快 10.93×** | 有损；需训练编码器 |
| **ProCut** | EMNLP'25 Industry | 生产 prompt 降 **73%/84%** | 有损（归因估计） |
| **CodePromptZip** | ACL'26 Findings | 代码 RAG **+23.4~28.7%** | 有损；需静态分析 |

### 3.3 软 token / 训练路线（有损 + 需微调）

| 工作 | 做法 | 局限 |
|:---|:---|:---|
| **Gisting**（ICML'23，被引 400+） | 训练 LM 把 prompt 压成 "gist token"，可缓存复用 | 需微调；**不可读**；压缩 token 不能用于原始未调模型 |
| **AutoCompressor** | 递归压缩，支持 **30,720 token** | 需微调 |
| **ICAE / xRAG / 500xCompressor** | 编码为特殊 token，4~16× | 不可读 |

### 3.4 Agent 上下文管理路线（时间维度）

| 工作 | 做法 | 实测 |
|:---|:---|:---|
| **ACON** | 优化压缩**准则**（非固定策略），并蒸馏到小模型 | peak token **降 26~54%** ｜ 小模型 **+20~46%** |
| **Active Context Compression（Focus）** | agent **自主**压缩自身轨迹（"Passive Retention → Active Compression"） | token **降 22.7%**（单例最高 57%）｜精度不变 |
| **Context as a Tool (CAT)** / **AgentFold** / **HiAgent** | 分层/主动上下文管理 | — |

> **注意**：3.4 这一类压的是**时间轴上的历史**（轨迹、观察）；
> **本方案压的是"常驻记忆"**（空间性的、每轮都在的）——**是两个不同战场**。

## 四、新颖性分析（诚实版）

### 4.1 **不是我们首创**的部分（必须承认）

| 要素 | 先例 |
|:---|:---|
| 用**短代号替换长概念** | ✅ CompactPrompt、Dict-Encoding、IBM 教程、LZW（1984） |
| **无损可逆**字典 | ✅ Dict-Encoding（2604.13066）、Harvill et al. 2025 |
| **免微调**（上下文内学字典） | ✅ Dict-Encoding（2604.13066）——**它已明确解决** |
| 代号**语义可读** | ⚠️ 部分（CompactPrompt 用 `ABC1`；Dict-Encoding 用 `⟨M1⟩` ——**都偏机器码**） |

### 4.2 **是我们的空白**的部分（可主张）

| # | 要素 | 现有工作的状况 | 我们的做法 |
|:--|:---|:---|:---|
| **1** | **★ 字典外置 + 惰性加载** | 🔴 **全部把字典放在 prompt 内部**（文档内 / system prompt 内）→ **字典本身照旧占额度** | **正文只留词名索引（262 字符）；字典独立成文件、按需读取** |
| **2** | **★ 以"截断安全"为设计目标** | 🔴 **无任何工作讨论此失效模式** —— 因为压在"总窗口够用"的前提下 | **明确把"静默尾部截断 → 代号变天书"当作首要故障来防** |
| **3** | **Agent 自维护的跨会话稳定代号表** | ⚠️ 相关工作多为**单次压缩**（一次性 encode/decode），非**持久、可累积、跨会话稳定**的词表 | **代号只增不改；跨会话、跨文件全局唯一** |
| **4** | **破掉"字典 vs 正文"零和关系** | 🔴 内嵌模式下：字典越大 → 正文越少（零和） | **外置后：字典增长不再挤压正文** |
| **5** | **条目强制带"可解析路径"+ 可达性校验** | 现有工作字典只有 `code → 原文` | 我们多一列：**`code → 含义 → 详情文件路径`**，且**路径必须真实存在（可机器校验）** |

### 4.3 一句话定位

> **相同的"缩写字典"内核，不同的"字典放置位置 + 失效模型"。**
>
> 现有工作问：*"怎么压得更多？"*（在总窗口够用的前提下）
> 我们问：*"在**常驻注入 + 硬上限 + 静默截断**下，怎么压得**无损且失效安全**？"*

### 4.4 建议的对外说法（避免夸大）

**❌ 不要说**："我们发明了字典压缩"（会被打）
**✅ 可以说**：
> "我们把**缩写字典**从 prompt **内部**移到**外部惰性加载**，
> 并把**注入截断安全**作为一等设计目标 ——
> 在 agent 常驻记忆（硬上限 + 静默尾部截断）场景下，实现**无损、失效安全**的额度压缩。"
